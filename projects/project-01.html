Overview

Filings Dashboard is a research tool for public-company filings. Pick a ticker, browse its recent 10-K, 10-Q and 8-K submissions straight from SEC EDGAR, chart the reported XBRL financials, and ask plain-language questions answered only from the filing text — with every claim cited back to the exact excerpt, section, and SEC.gov URL it came from.

Retrieval runs entirely on the machine it's installed on. Chunking, embedding and similarity search never leave the process; only the final answer synthesis calls an API. Indexing a 10-K costs nothing and works offline.

The problem

A 10-K runs to a few hundred pages of deliberately careful language, and the sentence that matters is rarely where you'd guess. Full-text search returns every instance of a word with no sense of which one answers your question. General chatbots will answer confidently about a filing they haven't read, and there's no way to check them.

The requirement I set was narrower than "summarise this filing": every specific number, date, or quoted phrase in an answer has to be traceable to the excerpt it came from, and the tool has to say so plainly when the filings don't contain the answer.

The retrieval pipeline

Dense retrieval, with the structure of the document doing more work than the embedding model:

Structure Filings are split on Item headings before chunking, so every chunk carries a real section label — "Risk Factors", "MD&A" — instead of a byte offset. That label shows up in the citation.
Chunking LangChain RecursiveCharacterTextSplitter, 1400 characters with 200 of overlap, splitting on paragraph → line → sentence → word.
Embeddings all-MiniLM-L6-v2 via sentence-transformers, run locally and normalised. ~90MB, cached after first use.
Store Chroma, persisted to disk. Indexing is idempotent — a filing already present is skipped, keyed on its accession number.
Retrieval Similarity search with relevance scores, top 8, with optional metadata filters on ticker and form type.
Synthesis Claude over the numbered excerpts, streamed so long answers don't stall the UI. The system prompt requires a citation for every figure and forbids answering beyond the excerpts.

Decisions worth defending

Filings are immutable once accepted, so extracted text is cached on disk keyed by URL and never re-fetched. The cache only needs invalidating when the extraction logic itself changes.

Embeddings stay local. Sending every chunk of every filing to an embedding API would cost real money per document and make the tool useless offline. A small local model is enough when the corpus is one company's filings rather than the open web.

Retrieval failure is a first-class outcome. When nothing matches, the pipeline says so and names what filing or section would hold the answer, instead of letting the model improvise. If credentials are missing, retrieval still runs and the matching excerpts are shown — a degraded answer beats an error page.

What I'd do next

The retrieval is deliberately plain — vector similarity and nothing else. No reranker, no hybrid keyword search, no query rewriting. For questions phrased close to the filing's own language it works well; for oblique ones it retrieves plausible-but-wrong sections, and a BM25 hybrid with a cross-encoder rerank is the obvious fix.

Beyond that: table-aware extraction, since financial tables currently flatten into text and lose their structure, and cross-filing comparison — "how did this risk factor change year over year" — which needs retrieval to reason across accession numbers rather than within one.
